# 屏幕识别与通知自动入账设计

日期:2026-10-15 · 项目:happy_spending
上位文档:`2026-10-10-bookkeeping-app-design.md`、`2026-10-13-apple-pay-auto-record-design.md`
本文取代 Apple Pay 文档里"不做微信、支付宝"的一条;与上位文档冲突时以本文为准。

## 1. 目标与范围

把微信和支付宝的支付自动记进来。按"付款发生在哪"分成两条路,一笔付款只会走其中一条:

| | 场景 | 怎么触发 |
|---|---|---|
| **屏幕识别** | 在微信、支付宝**里面**直接支付(扫码、被扫) | 付完款在支付页,双击手机背面或按操作按钮 |
| **通知** | 在**其他 app** 里付款、渠道选微信或支付宝(比如美团选微信支付),微信/支付宝会发出支付通知 | 全自动,收到通知就记 |

**做:**

- 两个快捷指令动作:"记一笔(屏幕识别)"和"记一笔(通知)"。
- 解析支付宝和微信的支付通知(各一种格式)。
- 解析三种屏幕页面:微信·支付成功页、微信·账单详情页、支付宝·账单详情页。
- 支付宝账单页自带的分类,通过映射表对应到我们的分类。
- 设置页"自动入账"帮助页补上两套快捷指令的搭建步骤。

**不做:**

- 支付宝·支付成功页(还没有样本,拿到后补规则)。
- 银行 app、云闪付等其他 app 的通知(没有样本)。
- 收入、退款、转账的记录:只记支出。
- 跨来源的重复检测和基于时间的去重:一笔付款只会走一条路。唯一保留的是"单号相同就跳过"。
- 不保存图片、识别出的原文和通知原文。
- "一键添加快捷指令"按钮:等快捷指令在真机上搭好、分享出链接后再接,不在这一轮。

## 2. 为什么是这个方案

- **在微信或支付宝里付款时,这个 app 正在前台,iOS 不会为前台 app 弹出它自己的通知**,所以快捷指令的"收到通知时"触发器根本不会触发。作者实测:不管扫别人还是被扫,在 app 内付款都没有通知。这就是必须有屏幕识别这一条路的原因。
- **从其他 app 跳转到微信或支付宝付款**时,微信、支付宝会发支付通知,iOS 27 新增的"收到通知时"触发器能拿到标题和正文,这条路可以全自动。
- 屏幕识别用快捷指令的"拍摄屏幕截图"和"提取图像中的文字"两个动作,识别在手机本地进行。"拍摄屏幕截图"动作把图像交给快捷指令往下传,**不会存进相册**(需真机确认,见 §11)。
- 文字交给 app 之后,解析在 app 里用规则完成,放在 Core 可以用 `swift test` 测,快捷指令一侧不用写正则。

## 3. 数据模型

新增字段都是可选的,`EntrySource` 只是多了两个取值,靠 SwiftData 轻量迁移,已有数据不受影响。

### EntrySource 新增取值

`screenText`(屏幕识别)、`notification`(通知)。已有的 `applePay` 不变。账单行上三种都显示同一个"自动"标记。

### LedgerEntry 新增字段

| 字段 | 说明 |
|---|---|
| orderRefHash | `String?`,单号的 SHA-256 十六进制哈希;没有单号就是空。只用于"单号相同就跳过",存哈希不存原文 |

### PaymentRecord(Core 里的值类型,不入库)

解析的统一输出,各种来源共用:

| 字段 | 说明 |
|---|---|
| source | `EntrySource`(`applePay` / `screenText` / `notification`) |
| cents | 金额,整数分,必须大于 0 |
| merchant | `String?`,商户名;没有就是空 |
| note | 账单备注:有商户用商户名,没有就用渠道名(`微信`、`支付宝`、`微信支付`) |
| eventDate | `Date?`,页面上的支付时间;读不出就是空 |
| orderRef | `String?`,单号原文,写库前哈希 |
| platformCategory | `String?`,支付宝账单页上的分类名,如"日用百货" |

### 解析结果

```
ParseOutcome:
  payment(PaymentRecord)    // 识别出一笔支出
  ignored(reason)           // 认得出,但不该记(收入、退款等)
  unrecognized              // 认不出是支付通知或支付页面
```

## 4. 解析规则

解析器放在 Core,输入是文字,不依赖界面,全部用真实样本做测试。

### 4.1 通知

输入是通知的标题和正文。

- **支付宝**:标题含"交易提醒",正文匹配 `你有一笔 <金额> 元的支出`。
  - **锚定整句模式取金额**。正文里后面的"领 2 元小荷包支付红包"是促销文案,不会被误取。
  - 匹配到 `元的收入` 的,结果是 `ignored("收入")`。
  - 备注为"支付宝",没有商户。
- **微信**:标题含"微信支付",正文匹配 `已支付 ¥<金额>`(`¥` 和 `￥` 都认)。正文不是这个格式的(已退款、收款到账等)是 `unrecognized`。备注为"微信支付",没有商户。
- 其他标题、其他 app 的通知:`unrecognized`。
- 金额支持千分位逗号、`¥`/`￥`,按 `AmountText` 的规则转成分(去掉货币符号、四舍五入到分、超上限拒绝)。
- 两种通知都**没有商户名**,所以这类账不参与商户记忆,分类是"未分类",用户事后手动归类。

### 4.2 屏幕文字

输入是"提取图像中的文字"的整段输出,按行处理(去掉首尾空白和空行)。先判断是哪种页面,再用该页面的规则。**规则锚定关键词而不是行号**,所以状态栏时间、电量、操作按钮弹出的提示这类噪音行不影响结果。

| 页面 | 判断 | 金额 | 商户 | 时间 / 单号 / 分类 |
|---|---|---|---|---|
| 微信·支付成功页 | 含"支付成功"和"完成",**不含**"当前状态" | 形如 `¥0.20` 的一行 | "支付成功"和金额行之间的一行 | 无时间,取触发时刻;无单号 |
| 微信·账单详情页 | 含"当前状态"和"转账时间"(或"支付时间") | 形如 `-0.20` 的一行 | 形如 `扫二维码付款-给X` 的行里的 X | 时间取"转账时间"下一行;单号取"转账单号"下一行 |
| 支付宝·账单详情页 | 含"账单详情"(或"交易详情")和"付款方式" | 形如 `-15.12` 的一行 | 金额行的上一行(跳过 `<`、"账单详情" 这类导航文字) | 时间匹配 `yyyy-MM-dd HH:mm:ss`;单号取"订单号"后的数字,首屏看不到订单号时用"金额 + 精确到秒的支付时间"标识这一笔(同一页连按两次只记一次);分类见下 |

- **符号**:账单页金额以 `-` 开头是支出,以 `+` 开头是收入,收入得到 `ignored("收入")`;支付成功页默认是支出。减号接受 `-`、`－`(全角)、`−`(U+2212),货币符号接受 `¥`、`￥`、`Y`。
- **支付宝分类**:在所有行里找去掉结尾 `>`/`＞` 之后恰好等于某个已知分类名的行,不依赖它的位置(它和"账单分类"标签之间隔着别的内容)。
- **商户清洗**:去掉开头结尾的符号和圆点(如 `•`、`●`),保留括号里的内容;微信对个人收款方会打码成 `**`,原样保留。
- **时间**:允许日期里夹杂识别错误。读不出完整的年月日时,`eventDate` 为空,入账时取触发时刻。作者的实测样本里就出现了 `2026·10 514E 17:37:40` 这种乱码。
- **没有任何页面匹配**:`unrecognized`。

### 4.3 支付宝分类映射

内置一张"支付宝分类名 → 我们的一级分类名"的表,只收确定的:

| 支付宝分类 | 我们的分类 |
|---|---|
| 日用百货 | 日用 |
| 餐饮美食 | 餐饮 |
| 交通出行 | 交通 |
| 服饰装扮 | 服饰 |
| 爱车养车 | 汽车 |
| 酒店旅游 | 旅游 |
| 医疗健康 | 医疗 |
| 住房物业 | 居住 |
| 数码电器 | 购物 |

使用时按名字找**未归档的支出一级分类**,找不到(被改名、被归档)就当没有映射。表里的对应关系以真机上看到的支付宝分类名为准,可以增补。

## 5. 入账规则

`AutoEntryRecorder.record(_ payment:now:calendar:in:)` 放在 Core,Apple Pay 的现有入口改为构造 `PaymentRecord` 后走同一条路径。

1. 有 `orderRef` 时算哈希;库里已有相同 `orderRefHash` 的账,直接返回"已记过这一笔(单号相同)",不新建。
2. 分类依次尝试:
   1. **商户记忆**(需要有商户,规则同 Apple Pay 文档 §4);
   2. **支付宝分类映射**(§4.3,只对屏幕识别的支付宝账单页有效);
   3. 都没有则不设分类,显示为"未分类"。
3. 日期取 `eventDate ?? now` 对应的当天(`DayStamp.stamp`),`createdAt = now`。
4. 新建一笔支出:金额、备注 = `note`、`merchant`、来源、`orderRefHash` 按上面填好。
5. 保存失败则回滚并抛错。
6. 返回一句结果,如 `已记 ¥15.12 · 支付宝`。

**学习分类**不变:编辑一笔自动账并改了分类后,有商户才学习。通知来的账没有商户,所以不学习;屏幕识别来的账有商户时会学习。

## 6. 快捷指令动作

两个动作,都不打开 app(`openAppWhenRun = false`),`perform()` 只做转调:

- **记一笔(屏幕识别)**:参数 `text`(屏幕文字,文本)。
  - `ignored`(收入等):成功返回"已忽略:收入",不报错。
  - `unrecognized`:**抛错**,提示"没有识别到支付页面"。因为是用户主动触发的,总得有反馈。
- **记一笔(通知)**:参数 `title`(标题)和 `body`(正文),都是文本。
  - `ignored` 和 `unrecognized` 都**安静地成功返回**("已忽略:不是支付通知"),不报错。自动化在后台运行,出错会弹提示,不该因为一条无关通知打扰用户。

两个动作都复用现有的共享数据容器和中文错误提示机制。

## 7. 快捷指令怎么搭

**屏幕识别**(一个普通快捷指令,可以做成 iCloud 链接一键导入):

1. 动作依次是:拍摄屏幕截图 → 提取图像中的文字 → 记一笔(屏幕识别),文本参数设为提取出的文字。
2. 设为操作按钮(设置 → 操作按钮 → 快捷指令),或轻点背面(设置 → 辅助功能 → 触控 → 轻点背面)。
3. 在支付成功页或账单详情页触发。

**通知**(自动化):

1. 触发器选"通知",来自 **支付宝**,筛选"标题 包含 交易提醒"。
2. 再建一个,来自 **微信**,筛选"标题 包含 微信支付"。(iOS 27 说一个快捷指令能挂多个触发器,能不能合并成一个要真机确认。)
3. 运行方式选"立即运行",动作选"记一笔(通知)",标题和正文分别接触发器的通知标题和通知正文。
4. 前提:这两个 app 的系统通知要开着,并且至少显示在"锁屏"或"通知中心"之一,只选"横幅"不行。

设置页的帮助页写入以上步骤。

## 8. 隐私

- app 不保存图片,不保存识别出的原文,不保存通知的标题和正文;解析完只留金额、商户、备注、日期、来源和单号哈希。
- 识别在手机本地进行,不联网。
- 通知触发器按"来自哪个 app + 标题包含"筛选,微信的聊天消息不会进到动作里。
- 快捷指令里如果额外加了"显示通知",会在锁屏上显示金额和商户,这是用户自己的选择。

## 9. 错误处理

- 屏幕识别认不出页面:抛错"没有识别到支付页面"。
- 金额解析失败、为 0、超上限:沿用 `AmountError` 的中文提示,不记账。
- 通知认不出或是收入:安静成功返回,不记账。
- 保存失败:抛错,不静默丢数据。
- 商户记忆指向的分类已归档或不存在:忽略记忆,继续尝试映射,最后是"未分类"。

## 10. 测试方案

Swift Testing,SwiftData 测试用内存容器。**测试用例直接取自真实样本**:作者提供的三个屏幕页面的识别文字和两条通知,把单号、卡号尾号等敏感部分替换成假值后放进测试夹具,版式和噪音原样保留。

- **通知解析**:支付宝支出 / 收入;正文里有第二个数字时只取"一笔 X 元的支出"里的;微信已支付;微信的已退款、收款、其他正文是 `unrecognized`;其他标题 `unrecognized`;千分位金额;全角符号。
- **屏幕解析**:三种页面各一份真实样本;噪音行(状态栏时间、电量、操作按钮提示)混在文字里不影响结果;日期被识别成乱码时 `eventDate` 为空;收入页面被忽略;打码的商户原样保留;分类行不在预期位置时仍能找到;不含支付页特征的文字是 `unrecognized`;减号和货币符号的各种写法。
- **分类映射**:映射命中、目标分类被改名或归档时落空、商户记忆优先于映射、都没有时是未分类。
- **入账**:来源、备注(有商户和没商户)、日期取页面时间或触发时刻;单号相同跳过、单号不同或没有单号不跳过;屏幕识别的账有商户时可学习,通知的账不学习;保存失败回滚。
- **迁移**:模拟器里用新版本覆盖旧版本,确认已有账单、分类、自动账都在。

界面和动作本身不写自动化测试,动作保持很薄。

## 11. 真机验证清单

依赖快捷指令、操作按钮、相册和微信支付宝,Mac 和模拟器上无法确认:

1. 操作按钮和轻点背面都能运行"屏幕识别"快捷指令;操作按钮弹出的提示是否会被截进图里(已知会,解析对噪音有容错)。
2. "拍摄屏幕截图"运行后,相册和"最近删除"里**都没有新增图片**。
3. 三种页面的识别文字顺序和格式与样本一致;换一个商户、换一种支付方式后依然能解析。
4. 支付宝支付成功页的识别文字(采集样本,用于补规则)。
5. 通知的两个触发(或合并成一个):筛选生效、立即运行、锁屏时也能运行。
6. 在其他 app 里用微信支付或支付宝付款,通知到达后自动入账。
7. 在微信、支付宝里直接付款确实**没有**通知(预期行为,由屏幕识别覆盖)。
8. 支付宝账单页的分类映射生效("日用百货"记为"日用")。
9. 在同一个账单页连续触发两次,第二次提示"已记过"。
10. 收入、退款类页面和通知被忽略,不会记成支出。
11. 免费账号证书 7 天过期后,动作失效,重装后恢复。

## 12. 假设与已知事项

- 解析规则依据作者 iPhone(iOS 27.0.1)上的真实样本。微信和支付宝更新后页面或通知文案可能变化,规则需要跟着调整;识别不出时屏幕识别会报错、通知会安静忽略。
- 支付宝支付成功页、商家付款(非扫码)、转账、红包等页面还没有样本,第一版不覆盖。
- iOS 27 通知触发器的细节来自评测文章,以真机为准:标题筛选的可靠性、一个快捷指令能否挂多个触发器、锁屏时通知正文能否拿到(取决于通知预览设置)。
- 通知来的账没有商户,基本都是"未分类",需要用户事后手动归类。
- 页面时间取"支付时间"而不是触发时间,事后补记也能落在正确的日期上。
